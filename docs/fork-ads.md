# Отключение рекламы в нашем форке

Это изменение предназначено только для `bekasojed-tech/tdesktop`.
Не отправлять его в `telegramdesktop/tdesktop` и не включать в PR для оригинала.
Рабочая ветка изменения — `codex/disable-fork-ads`; после проверки её нужно
объединить с `dev` нашего форка. Порядок обновлений — в [fork-workflow.md](fork-workflow.md).

## Настройка

`Telegram/cmake/fork_options.cmake` включает `TDESKTOP_FORK_DISABLE_ADS`
по умолчанию для всех конфигураций и платформ. Существующий каталог сборки
получит новую настройку при следующем запуске CMake. Изменение исходников само
по себе не меняет уже собранный EXE: приложение нужно пересобрать.

Для диагностического сравнения с прежним поведением можно явно передать
`-D TDESKTOP_FORK_DISABLE_ADS=OFF` при настройке CMake. Затем вернуть `ON`
и пересобрать: CMake запоминает явно выбранное значение в своём cache.
Если сборка вообще не подключает настройку форка, `core/fork_policy.h`
оставляет исходное поведение. Это не механизм определения официальной сборки:
изоляция обеспечивается отдельным репозиторием и запретом отправки в upstream.

## Как показывается реклама

- `Data::SponsoredMessages` в `data/components/sponsored_messages.cpp`
  запрашивает `messages.getSponsoredMessages`. Ответ живёт в памяти сессии,
  затем превращается в локальные рекламные сообщения в истории, верхнюю
  рекламную плашку у ботов или объявления при просмотре видео.
  Оба варианта `canHaveFor()` теперь возвращают `false` при включённой политике.
  Вызов для видео завершает callback пустым результатом; объявления и их медиа
  не загружаются. Оба варианта экрана истории используют этот общий менеджер.
- `Api::PeerSearch` в `api/api_peer_search.cpp` отдельно запрашивает
  `contacts.getSponsoredPeers`. При отключённой рекламе рекламная часть сразу
  помечается готовой и пустой, а обычный `contacts.search` работает как прежде.
  Это важно: простое удаление рекламного запроса оставило бы поиск ждать ответа.
- `Data::PromoSuggestions` в `data/components/promo_suggestions.cpp`
  получает `help.getPromoData`. Рекламируемый канал с флагом `proxy` не передаётся
  в `setTopPromoted()`. Сам запрос сохранён: тем же ответом приходят подсказки
  аккаунта и служебные объявления без флага `proxy`.

Политика находится в `core/fork_policy.h`; в существующих обработчиках
оставлены короткие проверки. Схема API, отрисовка, подписка Premium и настройки
аккаунта не переделываются. Скрытые объявления не создаются, поэтому обычные
пути учёта просмотров и кликов для них не вызываются.

Это отключает встроенные рекламные размещения Telegram. Обычные посты,
написанные администраторами каналов, сообщения ботов и реклама внутри внешних
страниц или мини-приложений неотличимы здесь от их обычного содержимого.

## Обновления оригинала

Сохранять изменение отдельным коммитом в нашем `dev`, обновлять через merge,
как описано в `fork-workflow.md`. Не использовать `reset` на upstream,
полную замену файлов нашей версией или стратегию `ours` для всего файла:
так можно потерять исправления оригинала. Конфликты разрешать по смыслу.

После каждого обновления:

1. Проверить подключение `fork_options.cmake`, значение
   `TDESKTOP_FORK_DISABLE_ADS:BOOL=ON` в cache и использование `core/fork_policy.h`.
2. Найти вызовы `GetSponsoredMessages`, `GetSponsoredPeers`, `GetPromoData`,
   а также новые пути рекламы в изменённой схеме API. Новые механизмы upstream
   не отключаются автоматически этой политикой.
3. Собрать Debug. На аккаунте без Premium проверить канал, чат с ботом,
   видео канала и поиск запросом длиннее трёх символов. Объявлений быть не должно,
   а обычные результаты поиска, история и воспроизведение должны работать.
4. При использовании рекламного прокси проверить отсутствие рекламного канала
   вверху списка чатов и сохранение служебных подсказок аккаунта.

Git сохраняет наши коммиты при merge, но не гарантирует отсутствие конфликтов
или изменений смысла без конфликта. Маленькие проверки уменьшают пересечения;
проверка после обновления остаётся обязательной. Отправка в remote `upstream`
локально заблокирована адресом `disabled://upstream`; явный URL может обойти
эту защиту, поэтому публиковать изменения нужно только в `origin` нашего форка.
